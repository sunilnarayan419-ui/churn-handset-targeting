## Data

The two supplied tables describe the same {{ results.n_customers }} customers. `Client.csv` holds account and equipment characteristics and `Record.csv` holds usage, billing, call-quality fields and the churn label. `Customer_ID` is present, non-null and unique in both files and the sets match exactly, so a validated one-to-one merge yields {{ results.n_customers }} rows with no multiplication or loss.

**Target.** `churn` equals 1 if the customer left 31 to 60 days after the observation date. The task is binary classification. Churn is {{ results.sample_churn }} in the file, far above market rates, so the sample is enriched with churners; rankings and relative lift transfer to a realistic population, but raw precision, accuracy and counts do not.

**Quality.** {{ results.eda.cols_missing }} of 100 columns contain missing values, concentrated in household demographics (up to {{ results.eda.max_missing }} for `{{ results.eda.max_missing_col }}`). Usage and billing fields are almost complete. Missing values are imputed or handled natively inside the modelling pipeline and are never filled using test data.

**Leakage review.** No single variable separates churners well (the strongest stand-alone ROC-AUC is 0.574), and the data dictionary contains no cancellation, port-out or retention-offer fields. The data carry no timestamps, so we cannot prove that every column was recorded before the outcome window and we cannot run a time-based validation. We treat both as limitations.

**Fairness.** The `ethnic` field is excluded from every model, because a protected characteristic must not be used to decide whom to contact. Other demographic fields (for example income and marital status) remain and should be reviewed for proxy effects before deployment.

**Currency and market.** The data state no currency; we assume US dollars, consistent with the handset prices and the US-style regional labels. This is an assumption, not a finding.
